## TimescaleDB and Citus

These appear on PostgreSQL connections where the extension is installed (`timescaledb` or `citus`), whatever server type was recognised.

- **TimescaleDB in the sidebar:** hypertables get their own **Hypertables** group (with a row count over all chunks) and continuous aggregates show as **Materialized views**. Timescale's own schemas (`_timescaledb_internal` with the chunks, `_timescaledb_catalog`, `timescaledb_information`, …) are left out of the tree; you can still query them in the editor. Hypertable rows are edited like table rows.
- **TimescaleDB section of the Performance tab:**
  - **Hypertables:** time column, chunk interval, chunk and compressed-chunk counts, total size and the retention policy (`drop_after`).
  - **Chunks:** newest first, with their time range, size and whether they are compressed. Filter by hypertable.
  - **Compression:** columnstore savings per hypertable (bytes before and after), segment by / order by, and the compression policy with its next run.
  - **Continuous aggregates:** how far each one is materialized (its watermark), how far that is behind now, real-time or materialized only, and the refresh policy's window, schedule and last run. **Refresh** runs `refresh_continuous_aggregate` over the whole range.
  - **Jobs:** every policy and user-defined action from `timescaledb_information.jobs` with its last and next run, runs and failures, and **Run now** (`run_job`). **Job errors** lists recent failures from `job_errors` (TimescaleDB 2.9+).
- **Citus section of the Performance tab** (on the coordinator):
  - **Distributed tables:** distributed or reference, distribution column, co-location group, shard count and size.
  - **Worker nodes:** every node with its shard placements and data, as a table and bars. **No new shards** drains a worker of new placements before you remove it (`citus_set_node_property(…, 'shouldhaveshards', false)`), and **Take shards** lets it receive them again. **Shards** lists each placement (filter by table).
  - **Co-location groups:** which tables share shard placement, with shard count, replication factor and distribution type.
  - **Distribute, reference, undistribute:** on **Distributed tables**, **Distribute…** asks for the table, distribution column, co-location (`default`, `none` or another table) and optionally a shard count, checks the column exists, and shows the exact `create_distributed_table(…)` before it runs. **Reference…** makes a small table a reference table copied to every node. **Shard count…** re-splits a distributed table (`alter_distributed_table`, cascading to its co-located tables), and **Undistribute** brings a table back to the coordinator (`undistribute_table`, cascading via foreign keys).
  - **Rebalance:** the moves the rebalancer would make now and the state of the latest background rebalance (including the error of a move that keeps failing). **Start rebalance** (`citus_rebalance_start`) and **Stop rebalance** (`citus_rebalance_stop`). Shard moves use logical replication, so the nodes need `wal_level = logical`.
- **TimescaleDB editors** (in the same panels):
  - **Create hypertable…** turns a table into a hypertable (time column, chunk interval, and optionally moving the existing rows into chunks).
  - **Columnstore…** on a hypertable sets segment by and order by and the compression policy (compress chunks older than …); **No compression policy** removes the policy.
  - **Retention…** sets the retention policy (chunks entirely older than the interval are dropped by a background job); **No retention** removes it.
  - **Create continuous aggregate…** builds `CREATE MATERIALIZED VIEW … WITH (timescaledb.continuous)` from a bucket width, group-by columns and aggregates such as `avg(temp), max(temp), count(*)`; **Refresh policy…** sets its window and schedule.
  - Each editor asks for its values, then shows the exact statements before anything runs.
- **Citus in the sidebar:** each table shows how it is distributed next to its name (`distributed by tenant_id · 32 shards`, `reference table`, `Citus local table`, or `single-shard` for schema-based sharding), and Citus' own schemas (`citus_internal`, `columnar_internal`) are left out. **Table info** adds the distribution column, co-location group, shard count and size, and lists every shard placement with its node.
- **Refresh**, **Run now**, the editors, **Distribute**, **Reference**, **Shard count**, **Undistribute**, the node actions, **Start rebalance** and **Stop rebalance** ask first, are audited, and are not available on read-only connections.

## Hosted PostgreSQL: Supabase, Neon, Azure, RDS and Aurora

- **Supabase: run as a user.** On a Supabase connection, **Run as** also has a **Supabase** picker:
  - **anon** runs as the anonymous key does; **authenticated** as any signed-in user (no user id).
  - **a user from auth.users** lists users (search by email, phone or id; only identity columns and metadata are read, never password hashes or tokens) and runs as that user.
  - Each choice sets the role and the JWT claims Supabase Auth would issue (`sub`, `role`, `email`, `app_metadata`, `user_metadata`, …) as `request.jwt.claims`, plus the older `request.jwt.claim.sub` / `.role` / `.email` that `auth.uid()` and `auth.role()` read on some versions. All of it is local to the run's transaction, which is rolled back unless you choose Apply.
- **Supabase in the Performance tab:** a **Supabase** section with:
  - **Auth users:** provider, confirmation, last sign-in, and anonymous, SSO and banned users. It also gives a summary of sign-ins and sign-ups in the last 7 days. It never reads password hashes or tokens.
  - **Storage buckets:** objects, size, whether a bucket is public, and its size and type limits.
  - **HTTP requests (pg_net):** queued requests and recent responses, with secrets in URLs redacted. This is how database webhooks and Edge Function calls from SQL leave the database. Edge Function logs themselves are only in the Supabase dashboard; SQL can't reach them.
  - **Cron jobs (pg_cron):** schedule, last run and failures in the last day.
  - The pg_net and cron panels appear when those extensions are installed.
- **Neon in the Performance tab:** a **Compute and branch** panel shows:
  - the project and branch this connection runs on, and whether the compute is the primary or a read replica
  - its estimated size in compute units (from `max_connections`)
  - connections, and the Local File Cache hit ratio (with the `neon` extension)
  Branches and compute start/suspend are in **Neon branches** (below).
- **RDS and Aurora in the Performance tab:**
  - **Parameter group:** the settings the parameter group changed from the PostgreSQL defaults, the `rds.*` and `aurora.*` ones, and changes waiting for a reboot. Advice covers `rds.force_ssl`, `pg_stat_statements` preloading, `work_mem`, `random_page_cost`, slow-query logging and more.
  - **Wait events:** active sessions by wait event in the style of Performance Insights, each with what it usually means. On Aurora it also shows the cumulative waits from `aurora_stat_wait_event()`. The Performance Insights history itself is only in the AWS console.
- **Supabase tree:** your own schemas come first. `auth`, `storage`, `realtime` and `vault` sit under a **Supabase** group, and Supabase's internal schemas (`extensions`, `graphql`, `pgsodium`, …) under **Internal schemas** inside it, collapsed. The migration ledgers (`auth.schema_migrations`, `storage.migrations`, …) are not listed.
- **Azure Database for PostgreSQL in the Performance tab:** an **Azure** section with:
  - **Platform:** primary or read replica, built-in PgBouncer, Query Store (`azure_sys`), intelligent tuning and other facts SQL can see.
  - **Server parameters:** the parameters changed from their defaults, the `azure.*` ones and changes waiting for a restart, with advice (TLS, `pg_stat_statements` preloading, logging, memory). Change them in the Azure portal or with `az postgres flexible-server parameter set`: Azure does not allow `ALTER SYSTEM`.
  - **Extensions:** every extension with whether it is allow-listed in `azure.extensions`, needs `shared_preload_libraries`, and is installed. **Create** runs `CREATE EXTENSION` for an allow-listed one (asks first, audited, not on read-only connections).
  - **Connection security:** TLS enforcement and the minimum version, password encryption, whether Microsoft Entra ID authentication is on and which Entra principals exist (`pgaadauth_list_principals`), and the members of `azure_pg_admin`.
- **Amazon RDS and Aurora: IAM sign-in.** In the connection editor, set **Sign-in** to **AWS IAM token**, enter the region (filled in from an RDS host name) and optionally an AWS profile (otherwise the default AWS credential chain: environment, `~/.aws`, SSO). The database user must be granted `rds_iam`. TLS is required.
- **Azure Database for PostgreSQL: Microsoft Entra ID.** Set **Sign-in** to **Microsoft Entra ID token**: through the Azure CLI you are signed in to (`az login`, the default), a browser sign-in, or a managed identity on an Azure VM. The user is the Entra user or group name the server knows. TLS is required.
- Tokens are fetched on every connect (and for a new editor session when the last one is about to expire: RDS tokens last 15 minutes, Entra tokens about an hour). They are kept in memory only and never saved with the connection.
- **Neon branches.** On a Neon connection, the branch button in the sidebar opens **Neon branches**:
  - Add a Neon API key once (Neon console → Account settings → API keys). It is checked, then saved encrypted on this computer; MotionQL shows only its last four characters.
  - Pick the project to list its branches. **New branch** starts from the parent's latest data, a point in time (ISO timestamp) or an LSN, with a read-write compute.
  - **Reset** brings a branch back to its parent's current state, and **Delete** removes it. Both ask you to type the branch name. The default branch and protected branches cannot be deleted. Create, reset and delete are audited.
  - **Open** connects to the branch with this connection's user, password and TLS settings (Neon copies roles to branches), and opens a SQL editor on it.
  - **Compare** (licensed: Branch schema compare) diffs the branch's schema against its parent, or another branch you pick. See Schema compare below.
- **Supabase branches and migrations** (licensed: Cloud branches). On a Supabase connection, the branch button in the sidebar opens **Supabase branches**:
  - Add a Supabase personal access token once (Supabase dashboard → Account → Access Tokens). It is checked, then saved encrypted on this computer; MotionQL shows only its last four characters. Nothing here changes your project.
  - Pick the project (the one the connection points at is chosen for you). MotionQL shows how many migrations production has applied, and lists the preview branches.
  - **Migration diff** shows the migrations applied only on the branch (what merging it would apply) and only on production (the branch is behind).
  - **Schema diff** compares the branch's schema with production's, read through the Management API's read-only query endpoint. Supabase's own schemas (`auth`, `storage`, `realtime`, `vault` and the internal ones) are left out.

### Schema compare (branches)

The Neon and Supabase branch diffs read the structure of both sides (tables, columns, constraints, indexes, triggers, row-level security and policies, views, materialized views, functions and procedures, sequences, enums and extensions; never rows) and list what differs, object by object: **+** only on the branch, **−** only on the other side, **~** different.

- **Show deploy script** gives the SQL that brings the other side (the parent, or production) in line with the branch, in one transaction, in a safe order (extensions, schemas, types and functions first; drops last). Statements that would lose data (dropping a table, column, schema, sequence or extension, or changing a column's type) are written **commented out**, so you choose to uncomment them.
- **Copy script**, or **Open in editor** on the other side (for Neon; for Supabase when the connection is production's database). The script is never run for you; in the editor the usual read-only and confirm rules apply.
- Objects that belong to an extension are not listed. Partitions inherit their parent's constraints and indexes, so only the parent's are compared.

## Azure SQL Database

**Performance** on an Azure SQL Database connection adds two panels to the SQL Server ones:

- **Resource use:** CPU, data I/O, log write, memory, workers and sessions as a share of the service objective, from `sys.dm_db_resource_stats` (15-second samples over the last hour). It also shows the edition, service objective (DTU or vCores) and data size. It names the resource that limits the database when it stays above 80%.
- **Automatic tuning:**
  - It lists the automatic tuning options (wanted and actual state) and the current recommendations: forced plans after a regression, and indexes to create or drop. Each recommendation shows its reason, impact and script.
  - Copy a script into an editor to review and run it yourself.
  - **Set option** switches `FORCE_LAST_GOOD_PLAN`, `CREATE_INDEX` or `DROP_INDEX` on, off or back to the default. It asks first, is audited, and is disabled on read-only connections.

## CockroachDB, YugabyteDB and Amazon Redshift

These servers speak the PostgreSQL protocol: connect with **PostgreSQL** and MotionQL recognises them. **Performance** (gauge icon) then lists the panels that fit the server: its own, plus the PostgreSQL ones it supports. The rest are not offered (CockroachDB and Redshift have no `pg_stat_statements` or `pg_blocking_pids()`; none of the three has PostgreSQL's vacuum and wraparound). DDL shown in a panel is never run for you: copy it into an editor. Actions ask first, are audited, and are disabled on read-only connections.

- **CockroachDB**
  - Tree and table details hide the internal `rowid` key of tables created without a primary key, so such tables are browse-only, as on PostgreSQL. Row estimates come from the optimizer's statistics.
  - **Statements:** `crdb_internal.statement_statistics` per fingerprint: total and mean latency, calls, rows, automatic retries, failures, full scans, last run. Filter internal statements and other databases; **Reset** clears the cluster's statistics. Seeing all users' statements needs `VIEWACTIVITY`.
  - **Ranges:** the ranges of the database with the tables they hold, size, leaseholder and replica localities (`SHOW RANGES … WITH TABLES, DETAILS`). Turn off sizes for a faster list on big databases.
  - **Regions:** the cluster's regions, the database's regions and survival goal, and each table's locality, with `ALTER TABLE … SET LOCALITY REGIONAL BY ROW / GLOBAL / REGIONAL BY TABLE` (or `SET PRIMARY REGION` for a database that isn't multi-region yet).
  - **Changefeeds:** `SHOW CHANGEFEED JOBS` with status, tables, sink (passwords and keys redacted), format and lag behind the high-water mark; **Pause**, **Resume** and **Cancel**.
  - **Jobs:** schema changes, backups, restores, imports and the rest from `SHOW JOBS`, with progress, running time and errors. Filter by active or failed, and show automatic jobs if you want them. **Pause** and **Cancel** ask first; **Resume** doesn't.
  - **Contention:** lock waits per table and index over a time window, from `crdb_internal.transaction_contention_events`. It shows how many waits there were, the total and longest wait, and the most contended key. New waits appear after about 30 seconds.
  - **Hot spots:** load per store (queries, writes and CPU per second, leases and ranges) and the biggest ranges of the database. It warns when one store carries far more load than the others. Queries per second for each range are not readable from SQL; the DB Console's Hot Ranges page has them.
  - **Transaction retries:** when a statement fails with SQLSTATE `40001` (`restart transaction`), the error in the editor explains why (for example *another transaction wrote the same key first*), that nothing was kept, how to retry, and how to make it rarer.
  - **Explain** shows CockroachDB's own text plan as a tree (it has no `EXPLAIN (FORMAT JSON)`); run `EXPLAIN ANALYZE` in the editor for timings.
- **YugabyteDB**
  - **Statements** and **Activity & locks** work as on PostgreSQL. Visual Explain works too.
  - **Nodes & tablets:** the universe's nodes (`yb_servers()`) with cloud.region.zone, connections, CPU and memory, and the tablets of this database on the node you are connected to (`yb_local_tablets` only sees its own node; the master UI on port 7000 shows the whole universe).
  - **Sharding & tablets:** per table and index, HASH or range sharding, hash key columns, tablet count, colocation and range split points (`yb_get_range_split_clause`), with a re-shard helper: `CREATE TABLE … (LIKE … INCLUDING ALL) SPLIT INTO n TABLETS` (or `SPLIT AT VALUES` for range tables) and the copy.
  - **Geo-placement:** tablespaces with their `replica_placement` (replicas, placement blocks, leader preference) and how many tables and indexes use them, and a `CREATE TABLESPACE` example built from your universe's zones.
- **Amazon Redshift**
  - Tree and table details come from `svv_tables` / `svv_columns`. Each table shows its design next to its name (`DISTKEY(customer_id) · SORTKEY(sold_at +1)`, or `ALL` / `EVEN` / `AUTO`), and table details show the **DISTKEY** and **SORTKEY** instead of indexes. Redshift doesn't enforce primary keys, so a row edit is saved only when exactly one row matches.
  - The tree also lists **Spectrum tables** (external tables, with their location and format), materialized views (`svv_mv_info`, with auto refresh and staleness), late-binding views (marked `late-binding`), functions and stored procedures, and at the database level the **external schemas** (Glue / Hive catalog, database and IAM role) and **datashares** (producer or consumer, and the objects they share). The object view shows each one's properties and its DDL from `SHOW TABLE`, `SHOW VIEW`, `SHOW EXTERNAL TABLE` or `SHOW PROCEDURE`.
  - **Table design:** `svv_table_info` per table (distribution, sort key, size, rows, skew, unsorted %, stale statistics, compression) with advice: pick another DISTKEY when rows are skewed, `VACUUM SORT ONLY` when many rows are unsorted, `ANALYZE` when statistics are stale, add compression or a sort key. **Analyze** and **Vacuum sort** run from the row.
  - **WLM queues:** queued and running queries per queue with queue and execution time and slots (`stv_wlm_query_state`), and **Cancel query**. On Redshift Serverless (no STV tables) it shows the active queries from `sys_query_history` and the RPUs in use.
  - **Query history:** recent queries from `sys_query_history` (status, elapsed, queue and execution time, rows, result cache hits, errors). **Source** switches to the provisioned-cluster system tables (`stl_query`, `stl_wlm_query`, `svl_qlog`, with the WLM queue); clusters without the SYS views use them automatically.
  - **Vacuum & analyze:** per table, the unsorted share, rows marked deleted, how stale the statistics are and the sort benefit, with the advised `VACUUM` mode (`SORT ONLY`, `DELETE ONLY`, `FULL` or `REINDEX` for interleaved sort keys) and whether to `ANALYZE`. **Vacuum…** (pick the mode) and **Analyze** (`PREDICATE COLUMNS`) ask first, are audited and are refused on read-only connections.
  - **Explain** reads Redshift's text plan into the plan view: costs and rows per step, the `XN` operators, and the data movement of each join (`DS_DIST_NONE`, `DS_BCAST_INNER`, `DS_DIST_BOTH` …) with a warning on the ones that redistribute or broadcast a table.
  - **COPY from S3:** **New COPY…** in the Performance tab's **COPY from S3** panel builds `COPY <table> FROM 's3://…' IAM_ROLE … FORMAT AS CSV | JSON | PARQUET | ORC | AVRO` (or delimited text) with header lines, JSON paths, compression, manifest, date formats, empty and blank as NULL, truncation, max errors and region. The statement updates as you type and the confirmation shows exactly what will run. The panel lists recent loads (`sys_load_history`) and the latest load errors (`sys_load_error_detail`). COPY is audited (table and bucket) and refused on read-only connections.
  - **IAM sign-in:** choose **AWS IAM** as the sign-in method. MotionQL asks AWS for temporary database credentials when it connects: `GetClusterCredentials` for a provisioned cluster (for the user you enter, signed in as `IAM:<user>`; optionally created on first sign-in and joined to database groups) or `GetCredentials` for a Serverless workgroup (your IAM identity becomes the user). The cluster or workgroup and the region come from the endpoint host name (`….redshift.amazonaws.com`, `….redshift-serverless.amazonaws.com`); for any other host, set **Server type** to Amazon Redshift and enter them. It uses the default AWS credential chain, or the named profile you enter. The credentials stay in memory only, last 15 minutes, and are requested again for a new session after they expire and on every reconnect. TLS must be on.
  - **Results with no ceiling:** when a result has more rows than **Max rows**, the note above the grid offers **CSV** or **JSON**: the query runs again as a cursor in a read-only transaction and every row goes straight to the file (works on read-only connections too, since only a `SELECT` is accepted). The export is audited.
  - **UNLOAD to S3:** the cloud icon in the SQL editor (or **New UNLOAD…** in the Performance tab's **UNLOAD to S3** panel, which also lists recent UNLOADs) opens a form for `UNLOAD ('<query>') TO 's3://…' IAM_ROLE … FORMAT AS PARQUET | CSV | JSON` with partitioning, header, compression, manifest, overwrite or clean path, parallel and max file size. The statement updates as you type and the confirmation shows exactly what will run. UNLOAD is audited (format and bucket) and refused on read-only connections, where you can still build and copy the statement.

## QuestDB, Materialize, RisingWave and CrateDB

These servers speak the PostgreSQL protocol, so you connect to them as **PostgreSQL** (QuestDB on port 8812, Materialize 6875, RisingWave 4566, CrateDB 5432). MotionQL recognises them on connect and then reads each one's own catalog instead of PostgreSQL's:

- **Tree and table info.** Sources, sinks, materialized views and indexes show as what they are (PostgreSQL's `information_schema` would list some of them as tables). **Table info** also lists engine facts: QuestDB's designated timestamp, partitioning, WAL and indexed symbols; the Materialize cluster an object runs on; RisingWave connectors and formats; CrateDB shards, replicas, partitioning and column policy.
  - **CrateDB OBJECT columns** show as a tree of their sub-columns (`payload` › `geo` › `lat`). The table tab reads an object column whole, as JSON.
  - **QuestDB** has one schema, `public`. The table tab pages with QuestDB's `LIMIT lo, hi`.
- **Tree lines.** Each object shows its key facts next to its name: QuestDB `timestamp(ts) · by DAY · WAL` (plus dedup keys and TTL); CrateDB `6 shards · 1 replica · partitioned by (day)`; RisingWave `kafka · plain json · append-only` for a source and `iceberg · upsert → orders` for a sink; Materialize `kafka · in ingest` (and `stalled` or `failed` when a source or sink is not running). CrateDB columns show CrateDB's own types: `object(dynamic)`, `text[]`, `geo_point`, `geo_shape`, `float_vector`, `ip`.
- **Editor completion** adds each engine's own keywords and functions: QuestDB `SAMPLE BY`, `LATEST ON`, `ASOF JOIN`, `timestamp_floor`, …; Materialize `SUBSCRIBE`, `IN CLUSTER`, `mz_now()`, `CREATE CLUSTER … REPLICATION FACTOR`; RisingWave `EMIT ON WINDOW CLOSE`, `SHOW JOBS`, `tumble`, `FORMAT … ENCODE …`, `SET PARALLELISM`; CrateDB `CLUSTERED INTO`, `PARTITIONED BY`, `OBJECT(DYNAMIC)`, `GEO_POINT`, `FLOAT_VECTOR`, `knn_match`.
  - **QuestDB clauses:** after `SAMPLE BY` it offers intervals (`1s` … `1y`), in `FILL(` the fill modes, after `ALIGN TO` the calendar options, after `LATEST ON` the table's timestamp columns (designated timestamp first), and after `LATEST ON … PARTITION BY` its symbol columns first.
- **Materialize in the editor:**
  - A **Cluster** picker in the toolbar sets the cluster for that tab only (`SET cluster`). MotionQL checks that the cluster exists first, because Materialize accepts any name and fails only at the next query. **Default** puts the tab back on the server's default.
  - **Live `SUBSCRIBE`:** run a `SUBSCRIBE` statement on its own and it streams into a **Live** result tab. First comes the snapshot, then every change as it happens, newest first, with `mz_timestamp` and `mz_diff` (+1 for an insert, -1 for a delete). The stream has a server session of its own, so you can keep running other queries in the same tab, and it keeps running while you look at another tab.
    - **Stop** ends it. It also ends at **Max rows** (the row cap), when you close the tab, when the connection is closed, or when nobody has read it for two minutes. The rows you have stay in the grid until you **Close** them or start another stream.
    - If the grid falls behind (a very large snapshot), MotionQL holds up to 5,000 updates and stops fetching until the grid catches up. Materialize keeps the changes meanwhile, so none are lost.
    - It runs as a cursor in a read-only transaction (`DECLARE … CURSOR FOR SUBSCRIBE`, then `FETCH … WITH (timeout = '1s')`), so it also works on read-only connections. It uses the tab's **Cluster** and schema.
    - A `SUBSCRIBE` inside a batch of several statements is not streamed: MotionQL collects the snapshot and about 3 seconds of changes (or up to the row limit) into the grid. Run it again for newer changes.
- **Create Kafka source (Materialize and RisingWave editors):** the antenna button in the editor toolbar opens a guided dialog for reading a Kafka or Redpanda topic.
  - Give the source name, the brokers (as the server reaches them), the topic, the format (**JSON**, **Avro** with a schema registry, or **CSV**), the envelope (**None**, **Upsert** keyed by the message key, or **Debezium**) and the security (plaintext, SSL, or SASL with PLAIN or SCRAM).
  - **Columns** are the fields of the message. **From a sample message** reads them from one pasted JSON message.
  - **Materialize** gets `CREATE CONNECTION … TO KAFKA` (plus `… TO CONFLUENT SCHEMA REGISTRY` for Avro), `CREATE SOURCE … FROM KAFKA CONNECTION`, and optionally a `<name>_typed` view with a typed column per field. A SASL password goes into a `CREATE SECRET`. The **Cluster** sets `IN CLUSTER`.
  - **RisingWave** gets `CREATE SOURCE` or `CREATE TABLE` with the Kafka properties in `WITH (…)` and `FORMAT … ENCODE …`. Upsert and Debezium need a table, so the dialog switches to one; upsert keys it by the message key. **Start from** sets `scan.startup.mode`.
  - Envelopes the format does not support are disabled with the reason. The SQL preview, **Copy SQL** and **Insert into editor** show the password as `********`.
  - **Create** runs the statements like the editor does: refused on read-only connections, confirmed on production ones, and audited.
- **Time-series quick chart (table tab; QuestDB tables over their designated timestamp):** when a table page has a time column (`timestamp`, `timestamptz`, `date`, …) and a number column, the table tab's bar shows **Chart**. Editor results use the result chart's **Grid / Chart** switch instead. One click draws the first number column as a line over the time column. Pick another **Time** column, or add up to three number columns as series (they share one axis, so chart columns of a similar scale together). Hover to read every series at that time. Times are shown in UTC, as in the grid. A large result is averaged into up to 1,000 time buckets. **Grid** goes back to the rows.
  - In a QuestDB table tab, **Chart** draws the current page over the table's **designated timestamp**.
- **Insights** (activity icon on the connection) shows each engine's own panels:
  - **QuestDB:** **Partitions** (range, rows, disk size, read-only, detached, Parquet, and partitions waiting to be attached), with **Detach** and **Attach**. Detach refuses the active (newest) partition. Attach needs the partition folder renamed with the server's `cairo.attach.partition.suffix` (`.attachable` by default); the panel shows which partitions are ready and says what to rename otherwise. **WAL** (transactions written but not yet applied, suspended tables and their error, with **Resume WAL**), and **Materialized views** (refresh state).
  - **Materialize:** **Freshness** (how far each object lags the wall clock, from `mz_wallclock_global_lag`; refreshed about once a minute by the server), **Clusters** (size, replicas, what runs on each; **System clusters** shows `mz_*` too) with **Replication factor…** and **Resize…** for managed user clusters, **Lineage**, **Replicas** (online or offline and why, CPU, memory and disk use, workers, credits per hour, and how many objects each replica has hydrated), **Sources & sinks** (status and error, messages and bytes, snapshot progress, offset lag) and **Hydration** (whether each materialized view and index is rebuilt on each replica).
  - **RisingWave:** **Streaming jobs** (`SHOW JOBS`: statements still backfilling, with their progress, and **Cancel job**), **Lineage** (from `rw_depend`), **Sources & sinks** (connector, format, Kafka consumer lag, sink decoupling; **Rate limit…** throttles a source, connector table or decoupled sink, `default` removes the limit), **Parallelism & rate limits** (status, parallelism, fragments and rate limits per job; **Set parallelism…** rescales one to a number or `adaptive`), **Worker nodes** (type, state, parallelism, memory, CPU, recovery) and **Event log** (failed jobs, barrier failures and recoveries; **Show all** adds routine barrier completions).
  - **CrateDB:** **Nodes** (master, version, heap, disk, load, shards and failed node checks), **Health & allocation** (tables that are not green, shards not started and why, failing cluster checks; **Allow allocation** sets `cluster.routing.allocation.enable` back to `all`, and **Retry failed allocations**), **Shards** (where each shard lives, and why an unassigned one is not allocated), **Partitions**, **Snapshots** and **Jobs** (running statements with **Kill**, recent ones and errors from `sys.jobs_log`).
  - **Lineage** draws the objects in columns, from sources on the left to what reads them on the right. Each node lists what it reads from. **Table** shows the same dependencies as rows.
  - Every action (**Resume WAL**, **Detach**, **Attach**, **Cancel job**, **Rate limit**, **Set parallelism**, **Replication factor**, **Resize**, **Kill**, **Allow allocation**, **Retry failed allocations**) asks first and shows the statement, is audited, and is not available on read-only connections.
  - **Ask AI** on each panel explains it in the engine's own terms (partitions and WAL on QuestDB, shards and allocation on CrateDB, sources, sinks, parallelism and hydration on the streaming engines), and the editor's AI writes SQL in each engine's dialect.
- **Explain** (list icon in the editor) runs the server's own `EXPLAIN` and shows its text plan as a tree in the plan view. There is no Explain Analyze.
- **Not available on these engines:** the PostgreSQL **Performance** tab (`pg_stat_statements`, activity, vacuum), the JSON plan with costs and timings, typed cell editors, row-level security, **Roles & privileges** and **Run as**. They say so instead of failing with a server error.
- **Read-only connections:** QuestDB and CrateDB accept a read-only transaction without enforcing it. MotionQL's own check still refuses every statement that is not a read.

## Db2, Firebird, H2, HSQLDB and Derby (JDBC bridge)

These engines are reached through a small JDBC bridge that runs on **your own Java** with **the JDBC driver JAR you choose**. MotionQL does not download or bundle Java or any JDBC driver. Browse, edit tables, the SQL editor, read-only connections and export work for all five. All five are rated *Good*: they add object DDL, Insights, Explain and test data (below; Db2 has its own section after this list).

- **Java:** Java 11 or newer, found through `MOTIONQL_JAVA` (a `java` executable), then `JAVA_HOME`, then the `PATH`. When none is found, the connection form says so; install a Java runtime (for example Eclipse Temurin, or your system's OpenJDK package) and click **Check again**.
- **Driver JAR:** click **Choose JAR** and pick the driver: `com.ibm.db2:jcc` (Db2), Jaybird `org.firebirdsql.jdbc:jaybird` (Firebird), `com.h2database:h2` (H2), `org.hsqldb:hsqldb` (HSQLDB), or `derby` + `derbyshared` (embedded Derby 10.15+) or `derbyclient` (Derby server). MotionQL shows the driver's version and records the JAR's SHA-256; if the file changes later, the connection refuses to load it until you choose it again. Each connection can use its own driver version.
- **Embedded databases** (H2 `.mv.db`, HSQLDB `.properties`, a Derby database folder): choose **Embedded** and **Browse** to the file. While MotionQL has it open, other applications cannot open it; MotionQL explains lock errors and suggests what to do. For H2, **Embedded, shared with other processes (AUTO_SERVER)** lets several applications use the file. MotionQL reads the H2 file header and warns when the file was written by a different H2 major version than the JAR (1.4 files need a 1.4 JAR).
- **H2 without Java:** choose **PostgreSQL server (-pg)** to connect to an H2 server started with `-pg` through MotionQL's PostgreSQL driver.
- **H2 compatibility mode:** pick the `MODE` the database was designed for; the connection info shows the mode in effect.
- **Firebird** has no schemas: tables are listed under **PUBLIC**, and Firebird `SET TERM` scripts run in the editor. **Db2** `--#SET TERMINATOR` lines and compound `BEGIN … END` blocks are kept whole.
- **Object view and Script as CREATE:** tables, views, sequences (Firebird generators), functions, procedures and triggers open in the object view with their properties (columns, primary key, indexes, row estimate), their foreign keys as dependencies, and their DDL; Firebird domains, exceptions and packages too (as a `SET TERM` script). H2 tables come from H2's own `SCRIPT`; the other engines' table DDL is built from the catalog with unique constraints, indexes and foreign keys.
- **Insights** for embedded engines: **H2** sessions (end another session with `ABORT_SESSION`), locks and table sizes; **HSQLDB** sessions and what they wait for (release or close another session), and table sizes; **Derby** transactions, locks and space used per table and index. MotionQL's own session is marked and cannot be ended.
- **Explain:** H2 (`EXPLAIN`, and **Explain Analyze** with `EXPLAIN ANALYZE`, which runs the statement), HSQLDB (`EXPLAIN PLAN FOR`) and Derby (the runtime statistics of a `SELECT`, which Derby only has after running it) show in the same plan view as PostgreSQL, with warnings for full scans.
- **Test data:** **Generate test data** works for Db2, Firebird, H2, HSQLDB and Derby too.
- **Insights** (activity icon on the connection): **Firebird → Attachments** lists `MON$ATTACHMENTS` and can disconnect one; **Db2 → Table statistics** shows row counts, pages, overflow rows and the last RUNSTATS of a schema's tables, with **RUNSTATS** and **REORG** row actions through `SYSPROC.ADMIN_CMD`. Actions ask first, are audited and are not offered on read-only connections.
- **Db2 Explain:** the **Explain** button of the SQL editor shows the access plan of the statement under the cursor in the same plan view as PostgreSQL, with its findings. Db2 writes plans into its explain tables, so MotionQL asks before creating them and does not offer Explain on read-only connections; there is no Explain Analyze for Db2.
- **Engine tools** (wrench icon on the connection):
  - **Backup:** H2 `SCRIPT TO`, HSQLDB `SCRIPT`, Derby `SYSCS_BACKUP_DATABASE` into a file or folder you choose. Firebird backups use the Services API (the same format as `gbak -b`): the backup streams from the server into a `.fbk` file you choose on this computer, so no `gbak` and no access to the server's disk is needed, and the database stays online. Read-only connections can take backups.
  - **Restore (Firebird):** choose a `.fbk` file and the database to restore into (a path or alias on the server; by default the connection's own database). Without **Replace the database if it exists** the restore creates a new database and stops if one exists; with it, the database is overwritten. MotionQL asks first, disconnects its own sessions when you replace the connection's database (other applications still attached make the server refuse), and records the restore in the audit log. Restores are not offered on read-only connections.
  - **Migrate to PostgreSQL or SQLite** (Pro): copies one schema's tables with their rows, primary and foreign keys, indexes and identity counters into a PostgreSQL connection or a new SQLite file. **Preview** shows the column type mapping and the DDL first. Names that are upper case only because the engine folds them (`ORDERS`) become lower case (`orders`). After the copy MotionQL compares row counts and a checksum of up to 1,000 sampled rows per table (by primary key) and reports any difference. Existing target tables stop the run unless you choose to replace them and confirm. **Save as task…** turns the settings into a **Migrate out** task you can schedule (see [More task kinds](/docs/tasks-cli)).

### IBM Db2

- **Tree from SYSCAT:** each schema lists tables, views, materialized query tables (MQTs), aliases, indexes, sequences, procedures, functions and triggers; **Tablespaces** and **Buffer pools** are listed under the connection.
- **Object view and Script as CREATE** build the DDL from the catalog the way `db2look` does: column types, identity and generated columns, defaults, primary, unique, check and foreign keys (with `ON DELETE`), indexes, `IN` / `INDEX IN` / `LONG IN` tablespaces, compression, column organization and comments. MQTs, aliases, indexes, tablespaces and buffer pools have DDL too, and dependencies come from `SYSCAT.TABDEP`.
- **Explain** reads the explain tables (operators, streams and predicates of the latest plan you explained) into the visual plan, with a warning for a large table scan that filters rows.
- **Insights** (`MON_GET_*` table functions):
  - **Sessions** (`MON_GET_CONNECTION`, the current statement from `MON_GET_ACTIVITY`): MotionQL's own session is marked; **Force application** (`FORCE APPLICATION`) asks first, is audited and never forces your own session.
  - **Lock waits:** who waits for whom, on which table and lock mode, with **Force the holder**.
  - **Top SQL** from the package cache by elapsed time, CPU, rows read or executions, with a text filter.
  - **Tablespace usage**, **Buffer pools** (hit ratios) and **Table statistics** (with **RUNSTATS** and **REORG**).
  - **Users and authorities:** database authorities, role memberships and table privileges; **Grant** and **Revoke** ask first and are audited.
  - Each panel has **Ask AI** (who is blocking whom, least privilege, which statements to tune).
- **Table actions** on a table's menu: drop, `TRUNCATE … IMMEDIATE`, empty, rename and duplicate (`CREATE TABLE … LIKE` plus the rows). Writes ask first and are not offered on read-only connections.
- The SQL editor completes Db2 keywords and built-in functions.
